# 食安链 UI 落地实施方案（供 Codex 执行）

把本文件和同目录的 `食安链-UI交互稿.html` 一起交给 Codex。下面是可直接执行的任务说明，不要再向用户追问设计方向；方向已经锁定。

---

## 0. 你要做什么

在现有仓库（Next.js 16 / React 19，包名 `delivery-audit`，产品名「食安链 · 餐饮原材料送货单识别与多项目比价」）里，按本方案落地一套围绕官方 Logo 的界面和核心操作体验。

先读本方案和 HTML 交互稿，再改代码。交互稿是视觉和交互的对照，不是要原样搬进生产（不要把 A/B/C 主题切换、预览画框做到正式产品里）。业务规则、API、Prisma 数据模型、OCR / 队列、权限校验，能不改就不改；现有 Vitest 必须继续通过。

每完成一个阶段，跑：

- `npm test`
- `npm run typecheck`

不要为了改 UI 去放宽测试或删断言。金额抹零、合同价拦截、识别恢复、权限隐藏单价等现有行为必须保留。

## 2. 硬性约束

- 仓库根目录就是本项目。不要扫描无关磁盘，不要改仓库外的文件。
- 不要改 Prisma schema、迁移、OCR 提示词、对象存储、登录鉴权，除非为完成下面某条体验所必需，并且要在说明里写清原因。
- 服务端权限检查必须保留。没有金额/单价查看权限时，仍然不能把数字渲出来。
- 金额计算沿用现有规则：`Math.round(quantity * unitPrice * 100) / 100`；已确认抹零、`amount === null`（无权限或待补）、批次模式等现有分支不要破坏。相关测试：`tests/rounding.test.ts`、`tests/item-checks.test.ts`、`tests/ocr-review-guard.test.ts`、`tests/view-permissions.test.ts`。
- 文案使用简体中文。
- 不要为了「好看」减少信息：异常原因、合同价、识别提醒、恢复副本提示都要在。
- 交互稿里演示数据（沪东农产品、鸡胸肉等）不要写进生产代码。

## 3. 现状问题（必须处理）

### 不好用

- 用词不统一：工作台 / 今日工作；新建单据 / 上传送货单 / 录入送货单 / 拍照录入；核对明细 / 单据校正。面包屑几乎总从「工作台」起，即使用户是从审核队列进来的。
- 手机主导航没有把「新建单据」放进底栏或「更多」，主操作只靠顶栏，不好找。原材料、供应商、项目经营、设置都塞进「更多」。项目经营和价格分析用了同一个图标。
- 单据核对应页（`src/app/(workspace)/documents/[id]/page.tsx` 约 60KB，加上 `DocumentItemsEditor.tsx` 约 24KB）过于拥挤：大量弹层，桌面分栏尚可，手机上对照原图改明细费劲。表格格子目前是点击后再弹层编辑，不是直接改，这是用户明确不满意的点。
- 单据中心筛选往往要再点一次「搜索」才生效，改了条件下面列表不变。
- `formatMoney(null)` 以及编辑器里 `unitPrice === null` 一律显示「未授权」。有权限但金额为空、识别未出结果时，应显示「—」或「待补」，只有确实无权限时才显示「未授权」。
- 侧栏 Logo 尺寸过大，见 1.2。

### 不好看

- 同时存在两套设计：`globals.css`（`@layer legacy`，墨绿 + 珊瑚）和 `design.css`（自称权威，棕色，但把原强调色都指到棕色）。登录页气场被盖成偏平米色，状态色、链接、主按钮区分度弱。
- 根布局一次引入 7 个全局 CSS：`globals.css`、`extra.css`、`design.css`、`ledger.css`、`compact-review.css`、`business.css`、`batches.css`，合计约 140KB，层叠覆盖多，改一处容易牵动别的页。
- 页面骨架大体正确，但间距、字号、层级像改到一半。

### 会拖累改界面的结构问题

- 原材料页约 36KB，设置页 `SettingsClient.tsx` 约 22KB，核对应页和明细编辑器也很重；能在改 UI 时顺手拆的再拆，禁止无关的大重构。
- 整站 `force-dynamic`，每次请求拉品牌配置。这次不必做缓存大改，不要把品牌注入弄坏即可。
- 权限模型本身细、服务端有校验。但侧栏对部分基础资料入口几乎总是显示，主要靠页内再判断。导航显隐应与权限对齐。

## 4. 分阶段执行（按顺序提交）

建议每个阶段单独提交，消息写清做了什么。不要把四步揉成一个无法回看的大提交。

### 阶段 1：统一设计规范（几乎不改功能）

1. 以 `design.css` 为唯一 token 来源，按第 1.1 节写入色板。
2. `globals.css` 的 legacy 色不再作为生效主色；旧选择器只保留必要兼容，颜色走新 token。
3. 修正 `--forest` / `--coral` / `--blue` 的错误别名，恢复状态色和主按钮的区分度。
4. 缩小侧栏 Logo，无上传 Logo 时回退到 `favicon.svg`。
5. 登录页左侧用 `--brand-pressed` 到 `--brand` 的深色区 + 浅色字 + 官方 Logo，金色只做点缀，不要再做成一片发闷的浅米色。
6. 主按钮、描边按钮、危险按钮、输入框、卡片、表格、标签（pill）在各页观感一致。

验收：登录、工作台、单据中心、核对页、审核队列在桌面和约 390 宽下，主色都能看出是 Logo 棕，成功/警告/错误仍可区分；Logo 不再撑满侧栏。

### 阶段 2：信息架构和用词

1. 导航与页面标题统一用词：
   - 「工作台」（不要用「今日工作」做同一页的另一个名字）
   - 「新建单据」（页内动作可写「拍照或选图」，但导航和主按钮用「新建单据」）
   - 「单据中心」
   - 「核对明细」（不要「单据校正」；主管进入时可称「主管审核」，但返回路径要正确）
   - 「审核队列」
2. 面包屑 / 返回：从审核队列进入单据时，返回和层级显示「审核队列」，不要一律写「工作台」。
3. 桌面侧栏：按权限隐藏无权限项（含原材料、供应商与合同、项目经营、价格分析、系统设置、审核队列、新建单据）。基础资料分组保留。项目经营与价格分析使用不同图标。
4. 手机底栏固定为：工作台、单据中心、中间 FAB「新建单据」（有提交权限才出现）、审核（有审核权限才出现，否则换成「更多」可放的入口）、更多。不要再把「新建单据」只藏在顶栏。
5. FAB 不得挡住核对页的「保存 / 提交审核」。核对页有底部操作栏时，缩小或收起 FAB（交互稿已如此处理）。
6. 「反馈建议」可留在顶栏或更多里，但要找得到，不要重复摆两个互不相通的入口搞乱层级。

验收：手机第一次进入就能从底栏新建单据；无权限的菜单不出现；用词在侧栏、顶栏、页标题、按钮上一致。

### 阶段 3：重做核心流程（重点，尤其是核对明细）

优先顺序：核对明细（桌面 + 手机）→ 单据中心 → 工作台 → 新建单据 → 登录 → 审核队列。

#### 3.A 核对明细（用户最关心，必须好改、好对照）

对标交互稿中的核对页，但接到现有数据、校验和抹零逻辑上。

**桌面**

- 左侧原图（可翻页、缩放），右侧明细表 + 当前行编辑区。
- 表格内「品名、数量、单位、单价」是真正的输入框 / 下拉，点击即可改，不必先点格子再开弹层。金额跟着重算（遵守第 2 节抹零与空值规则）。
- 选中行、改输入时不要整表卸载导致焦点丢失（不要一 `onFocus` 就重渲染把输入框卸掉）。
- 表头列宽用 `table-layout: fixed`（或等价方案），单位列要完整显示「kg」「桶」等，不能被裁成一个字母。
- 顶部用问题芯片列出待处理行（低置信、超合同价等），点击跳到该行，并与原图高亮同步（若原图已有行定位/高亮能力，接上；没有则至少滚动到对应明细行）。
- 主操作：「已核对，下一条问题」。普通提交在仍有未处理的错误级问题（如超合同价）时按现有规则拦截；不要改审核权限逻辑。
- 「保存」「提交审核」始终可及，不要用绝对定位挡住单价、金额或底部输入。

**手机（约 390 宽，这是验收重点）**

- 三个页签：**对照**、**原图**、**全部明细**。默认「对照」。
- 对照：上方原图缩略可滚动查看，下方是当前行表单（品名、规格、数量、单位、单价、金额），字段要够点、够改；「已核对，下一条问题」贴在表单下方，不能被底栏挡住。
- 全部明细：每行一张卡片，卡片内直接改数量/单位/单价；列表区域必须能滚动，最后一行（含底部门槛）要能完整划出来。常见错误是父级 `overflow: hidden` 而列表自己没有 `flex: 1; min-height: 0; overflow: auto`，不要再犯。
- 「保存」「提交审核」停在底栏上方（dock），不随列表滚走，也不要用 `position: fixed` 逃出布局而挡住内容。
- 减少重复大标题和长说明；问题用芯片，不要用占半屏的横幅。

**不要丢掉的现有能力**

- 增行、删除行、重新比对、单据信息与供应商、处理依据、撤回、删除单据、OCR 失败重试、恢复未提交副本、抹零确认与撤销。
- 这些可放进「更多」或次级面板，但要能找到，不要为了干净而删除。

#### 3.B 单据中心

- 行操作或行点击进入核对；按钮文案用「修改明细」或「核对明细」，与阶段 2 用词一致。
- 改筛选条件（状态、项目、日期、搜索词）后列表立即按新条件请求，不必再点一次「搜索」。若需防抖，搜索框可短防抖，但结果必须随条件更新。

#### 3.C 工作台、新建单据、登录、审核队列

- 工作台：待办清楚，主操作是「继续核对 / 修改明细」和「新建单据」。
- 新建单据：拍照或选图、张数限制等现有规则不变；手机主提交按钮始终可见。
- 登录：见阶段 1；演示或普通登录流程不要改接口。
- 审核队列：先处理有异常的单；强制通过必须填原因（已有逻辑保留）；可跳到核对页对照原图。

验收：在桌面和手机上，能直接改品名/数量/单位/单价，金额即时更新；手机「全部明细」可以划到最后一行；提交拦截行为与改前测试一致。

### 阶段 4：其他页面与结构收尾

- 项目经营、价格分析、原材料、供应商与合同、系统设置：套用同一套组件和色板，表格和表单好读、好点，不做无关功能改动。
- 改到过大的文件时，把核对页布局、明细表、问题芯片等拆成组件，避免再复制一套 CSS。
- 清理确定已经失效的重复样式，但不要为了「合并成一个 CSS 文件」做高风险全量搬迁。能把 token 和冲突清掉，比强行合成一个文件更重要。

## 8. 给执行者的工作方式

1. 先打开 `食安链-UI交互稿.html`（可用文件内的「手机 390」和「核对明细 / 全部明细」对照滚动与编辑行为）。

3. 每阶段结束后跑测试和 typecheck，再进入下一阶段。
4. 完成后用简短中文列出：改了哪些文件、核对页桌面/手机如何操作、哪些测试跑过、有什么有意没做的取舍。
