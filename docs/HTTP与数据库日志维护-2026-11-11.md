# HTTP、SQL与后台任务日志

本次增加结构化JSONL日志，不新增业务表或日志公开接口。2026-11-11已部署至现有服务器，Web、Worker与Nginx关联及公网页面复核通过；8个迁移无新增，业务22表、本地图片及已核验OSS对象摘要无变化。[发布记录](releases/2026-11-11-request-sql-logs.json)保存镜像、补丁、备份与实际验证。

## 记录范围

| 类型 | 内容 |
| --- | --- |
| HTTP | 请求编号、开始与结束、方法、路径、脱敏查询条件/请求体、用户编号、来源IP、内容类型与长度、状态码、毫秒耗时、慢请求标记、中途断开 |
| API与页面异常 | 错误类型、脱敏消息、调用栈、数据库错误码及cause；正常参数/权限拒绝为warn，服务器异常为error |
| SQL | queryRaw/executeRaw实际执行语句、占位符、参数数量、毫秒耗时、慢查询标记；连接、事务开始/提交/回滚也记录 |
| SQL异常 | 执行语句、耗时、SQLSTATE/Prisma错误码、可识别的中文原因与底层cause；失败后原异常继续交给原业务处理 |
| OCR Worker | 任务编号、单据编号、来源请求编号、开始/完成/失败与耗时；SQL沿用任务上下文 |
| Nginx | 所有到达代理的请求，包括应用收到前的拒绝；编号、路径、状态、总耗时/上游耗时、请求/响应字节数 |

浏览器响应头`X-Request-ID`是排查入口，可把HTTP、SQL、Nginx与排队OCR任务串联。日志是运行诊断，业务审计表`AuditLog`仍按原逻辑保存，不互相替代。SQL耗时为驱动调用耗时，包含连接等待/网络开销，不是数据库执行计划统计。

## 日志存放与保留

现网Web和Worker共享Docker持久卷`delivery_logs`，容器内目录`/app/.data/logs`，文件按服务`web`/`worker`、UTC日期、进程标识与序号命名。重建容器保留；不要运行删除该卷的命令。目录0700、文件0600，Docker内node用户可读。日志与业务数据一样只供授权维护人员访问，不提交GitHub。

默认每个服务每文件20MiB，最多30个文件或14天，以先达到的限制为准；总计约1.2GiB。每天或到大小后轮转，写入时检查期限/文件数，重启后继续清理匹配该服务的旧日志。低流量时清理在下一次写入进行。Nginx沿用现网每日轮转、保留14份、压缩的规则，访问日志路径`/var/log/nginx/shian-trial.access.log`。

写入采用异步批量队列，最多积压2048条。写盘失败降级到容器stderr，并输出`logging.write_failed`；超出队列时输出`logging.dropped`和累计计数。`/api/health`返回`logging.enabled/dropped/writeFailures/lastErrorCode`用于发现日志异常，不返回日志内容。计数随进程重启归零；硬断电或强杀可能丢失尚未写入的队列，不能把本机日志当异机归档或无限保存。

## 查日志

服务器上执行，默认输出最近200条JSON记录：

```sh
docker exec delivery-app-1 npm run logs -- --request 请求编号
docker exec delivery-app-1 npm run logs -- --level error --limit 100
docker exec delivery-app-1 npm run logs -- --event db.error --since 2026-11-11T00:00:00Z
docker exec delivery-app-1 npm run logs -- --event db.query --request 请求编号
docker exec delivery-app-1 npm run logs -- --job OCR任务编号
docker logs --since 30m delivery-app-1
docker logs --since 30m delivery-worker-1
```

查询命令流式扫描，只保留指定数量的最近匹配记录；支持`--request/--job/--level/--event/--since/--limit/--dir`。时间使用带时区的ISO格式，JSON中的`timestamp`为UTC。查Nginx时按同一编号搜索访问日志，跨天记录可能已在轮转压缩文件中。定位后按HTTP状态与错误事件、SQL错误码/原因、慢查询耗时的顺序检查。

## 内容边界与配置

密码、Cookie、Authorization、令牌、密钥、微信授权码、手机号/联系人/邮箱等敏感字段脱敏；不记录请求Cookie或完整头、SQL绑定参数值、响应正文或上传文件原文。SQL内嵌字面量/注释也隐藏。JSON请求保留有限字段/数组与文本，注明截断；未进入解析器的请求最多观察16KiB，过大、压缩、二进制或非法JSON只记长度/省略原因。Excel与Logo的multipart仅记录表单字段与文件名/大小/类型。直传OSS文件内容不经过应用HTTP日志，应用记录签名/完成确认等接口，云侧传输错误仍需结合OSS日志与浏览器错误。

这些规则处理项目结构化日志，第三方软件自身控制台输出和Nginx原生error.log仍按原有机制生成，应限制访问，不对外发送原始日志。自由文本也可能包含业务信息，诊断文件交给外部前仍按实际内容核查。

环境项在`.env.example`和`deploy/env.production.example`；Compose固定持久目录，不会被相对路径覆盖：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| LOG_ENABLED | true | 关闭时停止结构化HTTP/SQL日志；测试环境默认关闭 |
| LOG_SQL_MODE | all | all记录全部；slow仅慢查询；其他值仅保留SQL错误 |
| LOG_SLOW_HTTP_MS / LOG_SLOW_SQL_MS | 2000 / 500 | 慢请求与慢SQL阈值 |
| LOG_MAX_FILE_MB / LOG_MAX_FILES / LOG_RETENTION_DAYS | 20 / 30 / 14 | 单文件大小、每服务文件数、保留天数 |
| APP_LOG_DIR | .data/logs | 本地目录；现网Compose固定/app/.data/logs |
| RELEASE_ID | unknown | 发布标识，现网部署时写入.env |

HTTP日志由`scripts/server.ts`在Next处理器外采集，开发与生产统一使用`npm run dev/start`；直接运行`next start`会绕过HTTP采集。systemd使用`BIND_HOST=127.0.0.1`保持仅本机监听。Next页面错误同时接入`src/instrumentation.ts`。驱动边界代理覆盖PostgreSQL和本地PGlite，保留原返回值及异常。Nginx格式参考`deploy/nginx-observability.conf`，保留当前TLS配置再配置请求编号转发，不整份覆盖站点。
