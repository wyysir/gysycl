# 10张独立单据批量识别与集中核对方案

日期：2026-11-04。状态：**方案及交互演示，待用户确认；正式功能未实施、未部署。**

本次交付：本方案、[可点击演示](demo.html)、手机/电脑样图和原型检查记录。演示使用虚构样单，没有访问相机、上传照片、调用模型或操作业务数据库。预览服务只监听本机127.0.0.1。线上版本仍以原发布记录为准，本轮没有检查或变更服务器运行状态。

## 1. 已确认的需求

| 项目 | 本次设计依据 |
| --- | --- |
| 批次与单据 | 一批最多10张照片，同属一个项目点；每张是独立单据，自动关联自己的图片。同供应商只在页面集中展示，不合并单据或金额。 |
| 手机入口 | 安卓、苹果手机微信内，提供“拍照添加”和“从相册选择”；拍完可继续添加到本批，最多10张。 |
| 日期 | 优先采用原单明确日期；没有原单日期时沿用所选日期，每张可在资料弹窗修改。无法确定日期时保留原文并提醒，不能猜年份。 |
| 自动填写 | 读取供应商、材料名称、单位、数量、单价、行金额、原单总金额和日期。确定匹配的关联已有资料；不确定或不存在的，让员工确认关联或新建。 |
| 核对布局 | 全批明细连续展示，按供应商分组，明确区分每张单据；A版暖棕色，B版弹窗编辑。 |
| 提交方式 | 核对完一键提交，没有问题的先提交；失败、有问题或尚未核对的保留，稍后继续处理。提交后仍须主管审核。 |
| 准确率 | 用户选A：分别检验各类字段准确率，目标均不低于95%；手写与打印单大约各一半。 |
| 速度 | 一批10张，理想时间10秒内。计时建议见第5节，尚非已达到的性能承诺。 |

本次“每张独立成单”覆盖旧的“同供应商多页合单”要求，适用于新增批量入口。旧历史多页单据及其图片关系保留；旧入口是否继续提供另行在实施时整理，不批量拆历史单据。

## 2. 员工实际操作

1. 选择项目点与默认日期。一级页只展示已选信息，点击后在弹窗配置。
2. 拍照追加或相册多选，最多10张。缩略图显示第01–10张，可移除、补拍、放大。提醒“一张照片拍一张完整单据”。
3. 点击“开始识别”。每张上传完成后就进入独立识别，完成一张立即显示一张。进度分别显示上传、识别、成功、失败；不等待最后一张才显示全部结果。
4. 在同一核对页连续查看全部明细。供应商分组下，每张有日期、原图入口、明细和独立小计。默认显示全部，不只展示问题，否则员工容易漏看没有提醒的误读。
5. 点材料行打开编辑弹窗，对照该张原图修改。支持保存本行、保存并下一项；供应商、日期、原单总价在单据资料弹窗修改；未知材料在同级弹窗完成匹配或新建后返回。
6. 查看整张内容后点“确认本单”。识别完成、系统未发现异常，都不代表员工已经核对。再次修改影响核对结果的字段，撤销该张确认状态。
7. 底部点击“提交已核对（N张）”。先保存、由服务器重验版本和权限，再逐张送审。成功几张、失败几张分别反馈。已提交的不会重复提交，未成功的保留照片和已保存明细。

“确认本单”为建议交互，避免把机器识别成功误当成人工确认。用户确认方案后实施。希望减少点击时可在后续增加“确认当前已查看的无问题单据”，不能默认勾选从未核对的结果。

## 3. 核对页怎么排

- **一级页以明细为主**：顶部只有项目、日期、本批数量/状态及筛选，底部固定提交栏。完整系统单号收进资料弹窗，不占据主要工作区。
- **电脑**：供应商标题 → 每张单据细条 → 紧凑表格，数量、单价、金额右对齐；原图平时不占大块区域。编辑弹窗左边原图，右边当前行字段。
- **手机**：材料名称为主；次行显示“数量 单位 × 单价”，右侧突出金额。待确认提示直接出现在问题行。整行编辑入口，按钮保持可点击面积，金额不靠横向滚动查看。
- **二级弹窗**：手机上方显示本张原图入口，点开可放大并返回原编辑位置；数量、单位、单价、行金额集中输入；下一项方便连续修改。正式实现需保留未保存输入并适应软键盘和安全区。
- **状态明确**：识别中、识别失败、待确认、待核对、已核对、已提交审核。材料新建成功后立即更新本行匹配结果与提醒，保留其他真实异常，回归此前“已关联仍待处理”问题。
- **异常不过度打断**：低置信度及手写提示提供核对依据，不要求把每个提醒都改成“无提醒”。已核实的软提醒可按既有规则确认；严重校验错误和未关联资料继续处理。

演示中7张已经人工核对、2张有待确认字段、1张识别失败，这是虚构的过程状态，不表示识别后系统会自动确认7张。演示日期、金额、名称和图片均为合成内容。

## 4. 自动填写与“不出错”的约束

| 情况 | 处理方案 |
| --- | --- |
| 供应商完全确定 | 关联现有供应商；原识别文字保留可追溯。相似名称不给自动最终确认。 |
| 新/相似供应商、材料 | 员工选择候选或新建；同批相同文字可复用已确认的映射建议，但必须保留每张原文、版本和审计，避免一次误匹配传播。 |
| 单位或数字不确定 | 显示待确认，提供原图；不凭商品常识猜单位，不把斤/公斤直接等同，不自动进行包装换算。 |
| 数量×单价与行金额不一致 | 保留原单行金额，给出差额和核对提示；不能为“算对”而静默覆盖原金额。抹零等仍按既有规则处理。 |
| 原单总金额缺失或与明细不符 | 区分“原单未写”和“读取失败”，提示核对，不将明细和伪装成识别到的原单总价。现有软提醒与主管审核规则不擅自升级或删除。 |
| 识别失败 | 单张失败，其他单据继续；保留图片，支持员工主动重试本张、补拍或手工补录。 |
| 部分提交失败 | 按单据返回失败原因，保留修改；重试前查询服务器实际状态，避免响应丢失造成重复单、重复审核记录。 |

**批量“可提交”的拟议条件**：该张已人工核对、识别成功或已手工补齐、供应商与材料已关联、必填项齐全、保存成功、版本未变化、有提交权限且不存在未处理的严重错误。软提醒继续沿用既有确认规则，不用模型置信度直接阻断。

现场代码核查：现有`submitDocument`检查权限、状态、供应商、明细和材料关联；严重错误主要在主管“普通通过”环节拦截。本方案新增批量提交资格校验，**属于待实施的新逻辑**，不能写成当前已存在。主管普通审核/强制通过权限仍保留，不让批量提交绕过审核。

## 5. 10秒目标怎么做、怎么测

建议用户确认的口径：**已选好照片，点击“开始识别”起，至10张全部显示可核对明细止**，包括压缩、上传、排队、识别和写入；不包括拍照与人工核对时间。单张失败不算“10张全部成功完成”。同时记录首张结果时间、成功张数、上传与模型各阶段耗时。不要用动画、第一张出结果或离线批处理时长代替整批实测。

2026-11-04本地实际检查：上传并发2；Worker并发2；当前多页识别按页顺序调用；UI/API最多5页；现有压缩在较大图片上采用最长边3000、JPEG质量0.91，服务端处理也用3000/91。历史2026-10-31真实26图测试，模型响应平均约4.75秒/张。这不是当前微信10图整批耗时，不能拿平均值保证10秒。

拟优化顺序：

1. 10张拆成10个任务，一张完成上传即可入队，不等整批上传完；图片、结果与单据使用固定对应关系，完成顺序不会串图。
2. 保持一次请求/张。客户端压缩与上传采用小规模流水并行，服务端图片处理和远程模型请求分别限流；不要一口气同时解码10张大图耗尽手机或服务器内存。
3. 模型并发先测5，再视实际CPU、内存、延迟和账户限流测试提高至10。全局有上限和项目间公平调度，30个项目同时使用时不让单批独占；10秒目标先以单批正常网络条件测量，多项目高峰另报。
4. 复用已生成的处理图，减少重复下载、编码和长输出；优先优化调度和数据流，压缩参数暂维持现有基线。更小文件必须与基线逐字段对照后再采用，不能为快而压糊手写字。
5. 记录整批与每张阶段时长，汇总中位数、95分位、超时及10秒内全成功的比例；真实安卓/iPhone微信、正常Wi-Fi/移动网络分别记录。

**10秒是理想优化目标，当前未证实可达。** 单张模型波动、上行带宽和并发排队均会影响整批时间。若实测无法兼顾准确率，提供数据与可选方案给用户决定，不私自换模型、降清晰度或放宽95%标准。

沿用当前一次模型调用/张，无默认二次识别。用户尚未选择自动复核费用策略，本方案先保持现有成本规则；人工点击失败重试可能再次计费，超时也可能已计费，不能承诺只有成功才收费。若后续需要局部二次识别提高手写准确率，单列效果、额外费用和耗时，请用户另行确认。

## 6. 95%准确率验收

验收对象是**员工修改之前的结果**。分别计算供应商、材料名称、单位、数量、单价、行金额、原单总金额；日期作为额外必测字段。手写和打印分开统计，不能用打印结果掩盖手写问题，也不能把模型自报置信度当准确率。

- 建议准备100张有代表性的真实单据，50张手写、50张打印，多供应商、项目和常见拍照质量；60张用于改进、40张（20+20）保留为独立验收，不一边看测试答案一边改提示词。
- 参考答案先人工标注和复核。每个字段记“正确、错误、未输出、不可辨认/原单未写”。原单应有而漏掉的字段计错；漏行也进入明细字段分母，另外报告漏行与多行数。
- 不可辨认和本来没写的字段独立列数量及占比，保留样本；不计作正确，也不悄悄剔除只展示高分。无日期时正确使用所选日期属于回退规则通过，不算OCR读对原日期。
- 每类字段：正确数 ÷ 原单可判且应读取的字段数；每个手写/打印分组均至少95%。供应商及材料的最终关联是否正确另列，文字读对但关联错不能算整个业务字段正确。
- 数字按原单精度、单位按实际含义核对；不靠任意金额容差凑准确率。原单本身算错时，忠实读取与校验提醒分别评价。
- 报告同时展示样本量、逐项分子分母、整行全部正确率、整单全部正确率、漏行和幻增行。不把小样本95%表述为所有未来图片的保证。
- 速度试验建议在确认后的收费调用预算内跑至少10批×10张，并记录手机及网络条件；不把重复调用结果挑选拼成准确率。真机测试及业务参考答案需用户配合，脚本测试由助手完成。

历史基线仍有差距：2026-10-31手写明确品名28/33、手写单位30/34、完整可判日期15/17；打印明确品名111/111、打印单位107/112。部分模糊字段当时排除，且没有双人标注，见[原测试报告](../ocr-single-2026-10-31/使用与维护.md)。因此本次先建评测集验证，不能承诺只做批量并发就能达到95%。

建议数据结构：独立批次记录包含项目、创建人、默认日期和固定照片序号；每张现有Document关联batchId，继续复用单据权限、检查和审核。人工确认绑定单据版本，任何影响核对内容的修改都会使旧确认失效。新增字段需向后兼容；旧OCR结果和历史多页关系不重写。

安全与恢复纳入实现本身：批次列表及每张图片均检查权限；金额/单价/原图沿用现有可见权限，不因批量聚合泄漏；刷新从服务器恢复已有批次，未成功上传的图片不能保证微信关页后仍保留，应明确要求重新选择。无全批事务回滚成功单；照片失败重试复用本单任务身份，不新建重复单据。退出/断网时不得把本地暂存写成“服务器已保存”。

## 11. 2026-11-04确认后的实施说明

用户已确认并授权全面验证后部署。上文“未实施”“待确认”记录的是原型交付时状态。实际入口为“拍照录入”→每张独立上传并识别→批次核对→逐单确认→提交已核对的单据。

服务器保留批次及固定序号，刷新可恢复已上传部分；未上传照片可重新选择。每单确认记录绑定当前版本，修改、新建关联或重新识别后必须再次确认。普通员工、隐藏金额账号和其他项目账号沿用原权限；新入口不绕过主管审核。行编辑保存整个单据的当前草稿，原单金额不会随数量/单价自动改写；不一致需人工核对。历史多页单据继续使用原详情页。

目前采用单worker并发5、图片预处理并发2、客户端上传并发2，队列FIFO；没有承诺多项目公平调度或10秒SLA。相同单据版本只处理一次，重复创建/完成上传/提交均有服务器去重。网络失败可以重试本张；正在识别的5分钟内拒绝重复人工识别；超时后明确点击才再次调用模型。

部署前检查包括数据库/API权限与并发、四宽度实际组件、真实上传与模型链路，实际结果归档在`docs/releases/`。模拟API及原型检查不算真实准确率、速度或微信真机验收。95%指标仍按字段分别统计，不能用模型置信度替代。

本轮还核对了[OSS签名上传文档](https://www.alibabacloud.com/help/en/oss/user-guide/upload-files-using-presigned-urls)与[PutObject文档](https://help.aliyun.com/en/oss/developer-reference/putobject)。实测当前对象带版本ID，禁止覆盖头不能阻止覆盖，与官方版本控制说明一致。建单时将已校验字节保存到新的服务器专用原图键，单据只引用该键；上传链接只指向临时键，即使旧签名仍有效也不能改变已建单原图。临时对象删除为尽力清理；现有桶版本历史仍由原配置保留，未擅自修改生命周期或清除历史版本。

用户追加明确“图片压缩的方案也在本次部署”。上传前对≥1.2MiB图片尝试JPEG质量0.91、最长边3000像素、不放大；只有变小才采用，失败或不支持则沿用原文件。小图片不重复压缩，服务端识别仍使用原有3000/91处理基线。每次最多同时处理两张，避免手机一次解码十张大图。网站原图入口查看的是实际上传版本，大图成功压缩后不会同时上传手机原文件，手机本地原文件不改。历史图片不批量重压、不清理。

`scripts/verify-batch-compression.mjs`检查实际浏览器压缩函数，使用现有图片无损转PNG触发阈值；测试样本不是新拍的手机原件，压缩率不能直接外推所有照片。识别影响以真实模型对照记录为准，不能保证任意模糊小字均不受影响。
