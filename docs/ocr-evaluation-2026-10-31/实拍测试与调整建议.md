# 26 张实拍送货单：OCR 与 Qwen3.5-OCR 实测

日期：2026-10-31。状态：已完成真实 API 调用、人工看图核对与本地报告；未修改识别业务代码、未切换线上模型、未部署、无数据库迁移。

## 结论

1. 暂时保留现用 `qwen3.6-flash` 作为业务明细主识别器。这批照片的数字提取很好，主要问题在单位错位、少数手写品名、日期及不确定信息处理。
2. `qwen3.5-ocr` 已直接调用，不是仅查阅文档。测试了四种接入方式；原生关键信息抽取明显优于直接沿用现有提示词，但仍不足以整体替换主模型。简化字段版本的打印单表现接近现用方案，手写算式的数量、单价拆列明显较差。
3. 传统阿里云表格 OCR 可以考虑从“每图必调”改为可关闭的辅助通道；当前它只影响置信度，没有直接改善业务字段，也不是有效的结构化兜底。此项是建议，尚未实施。

## 样本与方法

- 用户指定目录 `测试图片/` 内共 26 张照片：15 张手写、11 张打印，人工核对 155 条前景可见明细，其中打印 112 行、手写 43 行。
- S12、S23 为同一张纸的不同拍摄，不能当成两张独立业务单据。S06 有手遮挡，只核对可见部分；不声称整张被遮挡的单据没有漏行。
- 以原图人工读数为标准，数量、单价、行金额分开核对，不用乘法计算值替代原单金额。手写名称不清楚则标为待确认，不用任何模型结果反过来充当标准答案。
- 打印数值分母为 `112 × 3 = 336`；手写数值分母为 128，排除 S22 有歧义的一个金额字段。打印单位单独核对 112 项；不把单位正确等同于材料名称正确。
- 全量主方案每图各调用一次、并发 3，不用“多次择优”合并结果。人工标签由一人核对，尚未由业务人员独立复核。这批样本不满足 README 中至少 30 张独立真实手写单的最终验收要求，不宣称总体准确率达标。
- 沿用当前预处理：Sharp EXIF 方向、最长边 3000、灰度/标准化、JPEG 91。没有在输入前手动转正；报告中的转正图仅便于人工查看。另在 6 张选样上测试了手动转正的影响，不能将该选样外推为全量效果。
- 当前源码基线：`d8153f0bda0d96d427fd4ff2869c6d101bf4faf7`。`src/server/ocr.ts` 统一为 LF 后 SHA-256 为 `3967afd07130ac6c0017cf0bde126309847ae18fd84a1a14b1bc82a87de27555`；只读核对服务器源码文本一致，原始字节因换行方式不同不能直接认定不一致。

“合计清洗”仅去掉“总金额:”等标题、转换原文明确的中文大写金额，不用明细累加补缺。简化版本在 S12 只返回“总金额:”而没有金额，S23 最后一行金额为空；两项均按缺失计。JSON 可解析和行数一致都不代表字段正确。

直接沿用原提示词的 10 次失败是返回文本不能解析为 JSON，并非模型不可访问；另一些虽然返回合法 JSON，却填入空明细或零值。该结果只说明直接替换接入不可用，不能作为 Qwen3.5-OCR 的最优能力结论。

### 接口与提示方式

- 现用主模型：`/compatible-mode/v1/chat/completions`，生产提示词与生产 `extractDocuments`。
- 直接替换：相同图片预处理及生产提示词，模型设为 `qwen3.5-ocr`；不传该模型不支持的强制结构化输出参数。
- 原生简短提示词：DashScope 多模态 generation，图片对象 `enable_rotate: true`，简短业务 JSON 字段要求。
- 原生抽取：同一原生接口，`ocr_options.task = key_information_extraction`、`task_config.result_schema`；读取响应 `ocr_result.kv_result`。带说明版本使用“供应商、送货日期、原单总金额、明细”等字段说明；简化版本为 `送货单位、日期、合计、明细[品名、单位、数量、单价、金额]`，值为空字符串。
- Qwen3.5 各方案均 `temperature: 0`、`max_tokens: 8192`、图片 `min_pixels: 3072`、`max_pixels: 8388608`。

原生任务和旋转参数应按[官方调用文档](https://help.aliyun.com/zh/model-studio/qwen-vl-ocr)接入；[模型能力表](https://help.aliyun.com/zh/model-studio/qwen3-5-ocr)列出的“不支持结构化输出”指不能依赖强制结构化模式，不能据此推断原生信息抽取任务不可用。即使返回 JSON，业务层仍必须校验类型、字段完整性和原图对应关系。

### 耗时与费用口径

上述五种方案总耗时中位数依次为 3.1、3.9、5.4、5.8、5.5 秒。现用方案计时包含本地传统 OCR 访问策略拒绝及预处理，其他方案包含预处理和接口调用；不是云服务器生产队列的端到端速度对照。

按实际 usage 与文档原价估算，26 次现用主模型约 0.198 元，26 次“带说明原生抽取”约 0.114 元；不是实际账单，不含传统 OCR、优惠、资源包或重试。此批调用成本差异不足以成为牺牲手写识别质量的理由。价格依据：[Qwen3.6-Flash](https://help.aliyun.com/zh/model-studio/qwen3-6-flash)、[Qwen3.5-OCR](https://help.aliyun.com/zh/model-studio/qwen3-5-ocr)。

## 传统 OCR 到底有没有调用、能否去掉

### 调用证据

线上配置为 `OCR_MODE=aliyun`、主模型 `qwen3.6-flash`，传统接口实际使用 `RecognizeTableOcr`。服务器容器用现有配置执行 26 次真实请求，**26 次成功**，保存了各次 requestId 和响应。

本地同密钥请求出现 `InvalidAccessKeyId.AccessPolicyDenied`，服务器成功，不能把本地拒绝误报为线上 OCR 失效。访问策略错误含义见[阿里云说明](https://help.aliyun.com/en/ram/support/faq-about-accesskey-pairs)。本轮测试验证“现在可以成功调用”，没有据此倒推过去所有用户上传是否都调用成功。

用户原截图选的是“OCR统一识别”，日期为 10月24—30日；本轮成功测试发生在10月31日，接口也不同。[表格识别 API](https://help.aliyun.com/zh/ocr/developer-reference/api-ocr-api-2021-07-07-recognizetableocr)属于通用文字识别，应核对相应产品、接口、账号和包含31日的统计范围。旧截图的0不能单独证明历史所有OCR调用为0。

### 当前实际作用

代码同时请求传统 OCR 和视觉模型；传统 OCR 文本没有送给视觉模型，而是抽取所有字符串、归一化后，用数量/单价/行金额的字符串在整页文本中的出现情况增加最多 0.12 置信度。没有同一行/同一列绑定，不校验品名，不会改正单位、数量、价格或补漏行。

固定本轮真实主模型结果，将真实服务器 OCR 响应分别带入和移除后，用未改动的生产提取代码离线回放：155 行的核心业务字段变化 **0 处**，置信度变化 **33 行**。这是确定性回放，不是重复调用云模型做随机比较，也不是“所有未来照片都不会受影响”的保证。

此外：

- 当前 `provider` 字符串固定写“aliyun-ocr+模型”，即使传统接口失败也可能这么显示，不能当成成功调用证据。
- 主模型失败时，即使传统 OCR 成功，程序也不能靠它恢复结构化明细；实际仍需人工录入/重试。
- 置信度为 0 或缺省时 `normalizeConfidence` 会回填 0.72；真实0与缺失未区分，需要单独修正。

### 移除的后果与实现边界

移除的是传统表格 API，Qwen 本身仍在读图，不是取消文字识别。按当前实现，主要影响为：少一次计费调用、少一项外部依赖、失去一份辅助文字证据、部分置信度降低而可能增加人工提醒。

两通道并行，移除不保证每张明显提速；传统接口超时/重试时才可能明显缩短等待。实施时应添加明确、可回退的辅助 OCR 开关，修正 provider 与告警，校准置信度及提醒阈值，再回归“主模型成功、失败、空明细、超时、多图缺合计”几种情况。不能只删 AccessKey 让所有请求报错；不能借此取消严重异常或抹零确认。
